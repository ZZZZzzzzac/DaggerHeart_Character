## Plan: SealChat 匕首之心角色卡

以 SealChat 单文件 HTML 模板为主，直接在模板内实现匕首之心角色卡与二元骰逻辑。这样模板可以同步掌握掷骰结果、即时调用 updateAttrs 回写希望点和压力点，并保留向聊天侧输出标准结果文本的能力；SealDice 插件改为可选兼容层，而不是主依赖。

**Steps**
1. 先定义模板数据契约与字段映射，统一 attrs 中“基础信息、六属性、资源、装备、经历、金币、自定义字段”的存储键名。优先复用现有 JSON 实例中的 Textbox/Checkbox 命名，避免迁移成本；对动态自定义字段新增单独容器键，例如自定义字段列表或键值数组。这个步骤会决定后续渲染、编辑和导入兼容策略。
2. 设计模板页面分区与交互模型。页面至少包括：角色抬头区、六属性区、资源区、等级/闪避/阈值区、经历区、武器与护甲区、金币区、自定义字段区、掷骰结果区。所有字段统一通过事件委托支持点击编辑，资源型字段支持加减按钮和直接录入两种操作。
3. 设计模板内二元骰模块。模块职责包括：掷 hope/fear 两枚 d12、解析优势/劣势和固定修正、生成总值、判定“希望结果 / 恐惧结果 / 关键成功”、产出结构化结果对象。这个模块与 UI 渲染分离，便于后续调整规则。若需要与现有 .dd 语法兼容，应在这里同时定义模板侧参数格式。
4. 设计掷骰后的 attrs 写回规则。希望结果：玩家希望点 +1；恐惧结果：不修改玩家资源，只在结果展示中标注 GM 恐惧点 +1；关键成功：玩家希望点 +1 且压力点 -1。这里要明确资源上下限策略：默认做 0 到槽位上限的钳制，避免越界。该步骤依赖第 1 步的数据契约和第 3 步的结果对象。
5. 设计聊天输出兼容层。模板在完成本地掷骰和 attrs 写回后，还需要生成一条可发送到聊天的标准结果文本。推荐方案是模板内直接拼装结果文案并通过模板模式发送；如果宿主仅接受 ROLL_DICE 结构而不支持任意文本，需要在计划中预留“结果文本映射到标准指令模板”的兼容策略。这个步骤与第 3、4 步并行细化，但最终行为依赖宿主可接受的消息格式。
6. 规划动态自定义字段能力。采用“可新增/删除键值对列表”的模型，字段项至少包含显示名、值、类型提示。模板提供新增、重命名、删除、编辑值的 UI；updateAttrs 时只更新自定义字段容器，不覆盖其他 attrs。这个步骤与第 1 步强依赖。
7. 规划导入兼容与初始化策略。模板收到 onUpdate 后，需要同时兼容已有匕首之心 JSON 实例和新建空白角色卡：已有字段按映射渲染，缺失字段回退为空值或默认值；动态字段容器不存在时自动初始化为空列表。应明确哪些历史字段在首版中只读忽略，例如 cards、背景问答、长篇日志等。
8. 规划可选插件兼容。现有 SealDice 二元骰插件不再是主流程，但可保留为聊天侧独立使用。若后续希望与模板结果文案统一，可在第二阶段再调整插件的输出文本和参数解析，使其与模板内规则保持一致。这个步骤不阻塞首版模板交付。
9. 明确实施顺序。第一阶段完成数据映射、基础布局、字段编辑和资源调整；第二阶段接入模板内二元骰与结果写回；第三阶段补充聊天输出、自定义字段和导入兼容；第四阶段做手工验收与边界修正。第 1、2 步阻塞全部后续；第 3、4、5 步可部分并行设计；第 6、7 步可在基础布局完成后并行；第 8 步明确为非阻塞。

**Verification**
1. 用空 attrs 和示例 attrs 各验证一次 onUpdate 渲染，确保模板在字段缺失、角色名为空、自定义字段为空时不报错。
2. 手动编辑六属性、等级、闪避、阈值、经历、武器、护甲、金币和自定义字段，确认 updateAttrs 发送的是局部 patch，且刷新后能正确回显。
3. 分别验证三种掷骰结果路径：希望结果、恐惧结果、关键成功。确认希望点和压力点的自动写回符合规则，且不会出现负数或超上限。
4. 验证手动资源增减与自动写回叠加后的状态一致性，例如压力点已为 0 时关键成功不会继续减到负数。
5. 验证模板模式下的聊天输出：至少确认能生成一条用户可理解且与模板显示一致的掷骰结果文本；若采用指令转发，还要验证聊天侧内容与模板本地结果不冲突。
6. 用现有示例 JSON 做一次兼容性检查，明确哪些字段首版渲染、哪些忽略但不会破坏模板运行。

**Decisions**
- 范围内：单文件 HTML 模板、模板内二元骰、玩家侧资源自动写回、聊天输出兼容、动态自定义字段。
- GM 恐惧点采用方案 A：不写入单个玩家人物卡 attrs，只在模板结果区和聊天输出中提示“GM 恐惧点 +1”，避免把共享资源错误绑定到个人卡。
- 范围外：宿主程序改造、cards 画布系统、背景问答和大段日志的首版完整编辑体验。
- 推荐以模板模式为主，不走宿主默认掷骰弹窗；否则模板无法稳定拿到最终结果并同步更新 attrs。
- 首版应优先保证数据正确性和编辑流畅度，不把大量现有 JSON 冷门字段都塞进界面，避免模板失控。

**Further Considerations**
1. GM 恐惧点建议在计划中作为单独设计决策处理：方案 A，只在掷骰结果文案中提示“GM 恐惧点 +1”，不持久化；方案 B，在当前人物卡 attrs 中增加一个共享型字段用于手动维护；方案 C，未来由宿主或群级存储统一管理。当前工作区内最稳妥的是方案 A，若你坚持要在卡内可见，则退而求其次做方案 B。
2. 聊天输出协议需要在实施前再确认一次宿主是否只接受 ROLL_DICE，还是允许模板直接发送结果文本；这会影响第 5 步的最终落地方式。
3. 自定义字段的数据结构建议尽早固定为数组对象，而不是平铺 attrs 键名；否则删除/重命名会导致历史垃圾键长期残留。
4. 如果后续希望与 SealDice 插件完全一致，最好把模板内二元骰的规则函数抽象为可复制到插件中的纯逻辑，避免两份规则长期漂移。
